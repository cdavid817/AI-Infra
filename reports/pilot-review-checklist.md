# 三章试点人工评审清单

评审范围：第 1、7、22 章。建议平台工程师与目标读者分别独立阅读，避免先看审计分数影响判断。

## 平台工程师：技术审阅

每项记录“通过 / 需修改 / 无法判断”，并附章节位置和反例。

- [ ] 第 1 章的能力迁移分类是否把治理方法与资源前提分开？是否存在被误判为“彻底失效”的经验？
- [ ] 第 1 章的同步任务无中断概率是否明确依赖独立性假设？公开案例与合成时间线是否容易混淆？
- [ ] 第 7 章的通信量公式、单位和有效带宽口径能否复算？Ring/Tree 曲线是否被清楚标为示意而非基准？
- [ ] 第 7 章诊断矩阵的顺序能否覆盖选路错误、物理链路退化、拓扑错放和算法错配？
- [ ] 第 22 章的每 token KV 字节数、显存扣减和并发换算是否遗漏运行时预留项？
- [ ] 第 22 章是否清楚区分 PagedAttention 的碎片收益与 KV 量化的单 token 字节收益？
- [ ] 第 22 章指标矩阵能否区分引擎内调度问题与网关、客户端问题？
- [ ] 三章所有精确数字是否都能归为公开来源、容量估算或合成数据？
- [ ] 是否存在语气强于证据、缺少适用边界或版本环境的结论？

## 目标读者：可读性审阅

- [ ] 阅读每章前两屏后，能否用一句话复述本章主问题？
- [ ] 是否有一段需要反复阅读两次以上？记录首次卡住的位置，不先提出改写方案。
- [ ] 图注是否直接说明“看哪里、得到什么结论”？
- [ ] 不看正文时，六张新图是否仍可能被误读为生产实测？
- [ ] `ChapterContext` 是否帮助定位，还是增加了页面噪声？
- [ ] `CaseMeta` 是否在不打断叙事的情况下说明了数据性质？
- [ ] 诊断矩阵是否比决策树更快找到自己的观测组合？
- [ ] 交付物是否能转化为实际计算、排障或决策记录，而非“理解概念”？

## 页面与无障碍检查

在浅色/暗色、桌面/窄屏各检查一次：

- [ ] SVG 文字无需缩放即可阅读，颜色不是唯一的信息编码。
- [ ] 图片点击可打开原图，alt 描述信息结构而不重复图注。
- [ ] 表格在窄屏可横向滚动，组件没有溢出正文栏。
- [ ] 图号连续，来源、许可与数据性质完整。
- [ ] 深色模式下 SVG、边框和正文对比度可接受。

## 通过条件

- 不存在公式、单位、来源或数据性质错误；
- 每章主问题能被两类评审者准确复述；
- 每章至少一张图被评审者用于完成判断，而非仅评价“好看”；
- 严重问题修复后重新执行 `npm run docs:check`、`npm run docs:audit` 和 `npm run site:build`。

评审通过后，按第 4、6、11、12、14、16、17、20、23、24、29、31 章顺序推进其余 P0 章节；每次只迁移一章并更新对比报告。

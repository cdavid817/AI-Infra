# Runbook 01:训练 hang(任务不退出、不报错、不前进)

## 现象

- 训练心跳告警:iteration 日志或步数计数器超过阈值(如 3 × 常态单步时长)不更新(指标定义见 [§20.4.3 故障检测](../第四部分-训练系统/第20章-稳定性与容错.md#2043-故障检测三类问题难度递增) 的第二类故障)。
- 全体卡功耗同时掉到待机水平、计算利用率归零——这是 hang 区别于"变慢"的强特征旁证。
- 进程存活、任务状态仍为 Running,没有任何错误日志;loss 曲线停止推进。
- 若集合通信 watchdog 已配置,可能伴随即将到来的通信超时报错(那属于 [Runbook 02](rb-02-nccl-hccl-timeout.md));本 Runbook 处理 watchdog 未触发或未配置、任务处于"无限等待"的窗口。

## 影响范围

- **单任务级**:hang 冻结的是一个训练任务的全部 rank——全局同步语义下,一个 rank 卡住,所有 rank 陪等。不会直接波及同集群其他任务。
- 但根因可能在**节点级**(某台机器硬件降速、失联)或**存储/数据面**(数据管道饿死),这类根因会在任务重启后复发,甚至击中下一个调度到该节点的任务。判定波及面:先确认同集群其他任务是否正常推进,再决定是否升级为集群级事件。

## 立即止损

1. **确认 hang 而非慢**:对比功耗/利用率曲线与步数计数器,两者同时停滞超过 2–3 个常态单步时长即判 hang。副作用:多花 1–2 分钟确认,但避免误杀一个正在做超长步(如恰逢同步 checkpoint)的健康任务。
2. **先采证据、再动进程**(采集项见下节)。副作用:hang 每多持续一分钟就多损失一分钟卡时;但跳过采集会让本次 hang 无法归因,同样的 hang 会再来一次。证据采集控制在 5 分钟内。
3. **终止任务并从最近 checkpoint 重启**:通过训练编排层下发停止,等待宽限期后强杀残留进程。副作用:回滚丢失自上一个 checkpoint 以来的全部训练进度(平均损失约半个 checkpoint 间隔 × 全任务卡数的卡时);强杀可能留下未清理的共享内存与设备残留状态,重启前需确认设备可用。
4. **若初判指向某个节点**(该节点功耗/心跳与众不同):重启前将嫌疑节点隔离出资源池,任务在其余节点(或补入热备节点)上重启。副作用:资源池可用容量减少;若误判,好节点被闲置,需依赖后续巡检归还。

## 证据采集

止损第 2 步执行,全部在杀进程**之前**完成——进程一死,现场即灭:

- **每个 rank 的调用栈**:对各 rank 进程抓 Python 栈与 native 栈(py-spy dump / gdb / 框架自带的 hang dump 工具)。这是 hang 分诊的核心证据,至少覆盖每个节点一个 rank,条件允许则全量。
- **设备侧状态**:每张卡的利用率、功耗、显存占用、时钟频率、XID/health 错误码(nvidia-smi / npu-smi 及其错误查询接口)。
- **通信状态**:各 rank 是否停在集合通信原语内(从调用栈判断);网络接口计数器与丢包/重传统计。
- **训练日志与步数**:每个 rank 最后一条 iteration 日志的步数与时间戳——用于判断"停在同一步"还是"步数不齐"。
- **数据管道状态**:dataloader 进程是否存活、数据源(存储/网络)是否可达。
- 采集方法与时间线分析口径统一遵循 [§5.4 Profiling 方法论](../第一部分-基础与心智模型/第05章-CUDA、CANN与加速器软件栈.md#54-profiling-方法论全书唯一定义处);监控指标口径见 [§29.2.4 训练侧可观测性](../第六部分-上层平台/第29章-可观测性与评测流水线.md#2924-训练侧可观测性与告警设计)。

## 诊断决策树

以"各 rank 最后步数是否一致"为第一分叉,以调用栈为第二分叉:

- **分支 A:所有 rank 停在同一步,且调用栈都在集合通信原语内**
  - 判定依据:步数一致 + 全员栈顶为 AllReduce/AllGather 等通信调用。
  - 含义:大家都进了通信,但通信本身不返回——问题在通信链路或网络。
  - 下一步:转 [Runbook 02:集合通信超时](rb-02-nccl-hccl-timeout.md) 的诊断树。
- **分支 B:大多数 rank 停在第 N 步的通信里,少数 rank 停在第 N 步的通信之外(计算/数据/IO 调用中)**
  - 判定依据:步数一致,但栈不一致——少数派没进通信,多数派在等它。
  - 含义:少数派 rank 是根因;看它的栈停在哪:
    - 停在数据读取/dataloader:数据管道饿死(数据源慢、卡在坏文件、预处理死锁),关联第 13 章。
    - 停在 checkpoint 保存/文件写:存储侧卡住,转 [Runbook 05](rb-05-checkpoint-stall.md)。
    - 停在计算 kernel 且该卡利用率异常/有错误码:硬件问题,转 [Runbook 03](rb-03-gpu-xid-ecc.md)。
    - 停在锁/队列等待:框架或用户代码死锁(常见:与训练线程抢锁的日志/监控线程)。
  - 下一步:对少数派 rank 所在节点做定点排查,按上述子分支处置。
- **分支 C:rank 之间步数不一致(有的在第 N 步,有的在第 N+1 步)**
  - 判定依据:各 rank 最后日志步数不齐。
  - 含义:同步语义被破坏——通常是集合通信调用序不一致(条件分支导致部分 rank 跳过某次通信、通信组构建不一致),或弹性伸缩/重启过程中的成员视图不一致。
  - 下一步:核对代码中按 rank 条件执行的通信逻辑;检查最近一次弹性事件/重启的成员列表;这类问题重启后大概率复现,需修代码而非换机器。
- **分支 D:某节点整体失联(采不到栈,心跳消失)**
  - 判定依据:证据采集在该节点上超时/失败。
  - 含义:节点宕机或管理面网络中断,任务表现为 hang 只是副产品。
  - 下一步:按 [§8.4.6 节点生命周期](../第二部分-算力底座/第08章-K8s上的加速卡.md#846-节点生命周期驱动健康检查与自动隔离) 隔离该节点,任务换节点重启;硬件报障走 [Runbook 03](rb-03-gpu-xid-ecc.md) 的隔离流程。

## 修复

- **分支 A**:按 Runbook 02 修复网络/通信问题后重启任务。
- **分支 B(数据管道)**:定位坏文件/慢数据源,修复或跳过后重启;为 dataloader 加读超时,把"饿死"转化为可见报错。
- **分支 B(存储)**:按 Runbook 05 处置存储侧,短期可切换为降低 checkpoint 频率或改用本地盘两级方案后重启。
- **分支 B(硬件)**:隔离故障节点(Runbook 03),补入热备节点重启。
- **分支 B(死锁)/分支 C**:代码修复(统一通信调用序、消除跨线程锁竞争),在小规模复现验证后再上大任务。
- **分支 D**:节点进检修池,由巡检系统离线定位;任务在剩余节点重启。
- 通用兜底:无论哪个分支,重启时必须确保集合通信 watchdog(超时机制)已开启并设置合理阈值——把未来的 hang 转化为会自我报告的第一类故障(机制见 [§20.4.3](../第四部分-训练系统/第20章-稳定性与容错.md#2043-故障检测三类问题难度递增))。

## 恢复验证

- 任务从 checkpoint 恢复后,连续 ≥ 30 分钟(或 ≥ 100 步)步数持续推进,单步时长回到事发前基线的 ±5% 以内。
- loss 曲线与事发前同一步数区间的历史曲线吻合(排除恢复错 checkpoint 或数据位点错乱)。
- 全体 rank 功耗/利用率回到训练态水平,无单卡持续偏离(否则转 [Runbook 04](rb-04-straggler.md))。
- 若更换过节点:新节点在任务内跑满一个 checkpoint 间隔无告警。

## 复盘数据

事后必须留存的量化项:

- **检测延迟**:最后一次步数推进的时间戳 → 首次告警时间。这是 hang 类故障最核心的改进指标;无心跳告警的集群此值常达 30 分钟以上。
- **响应延迟**:告警 → 开始止损动作。
- **中断总时长**:最后一次步数推进 → 恢复后首次步数推进。
- **损失卡时** = 中断总时长 × 任务卡数 + 回滚重算的步数 × 单步时长 × 任务卡数。
- **回滚距离**:事发步数 − 恢复 checkpoint 步数。
- 根因分支(A/B/C/D 及子类)、是否复发(同根因 30 天内二次出现)。
- 以上数据进入 [§20.4.2 有效训练时间占比](../第四部分-训练系统/第20章-稳定性与容错.md#2042-有效训练时间占比稳定性的唯一北极星指标) 的月度核算。

## 长期防复发

- **三层 hang 检测全部落地**:训练心跳告警、集合通信 watchdog、功耗/利用率旁证交叉确认([§20.4.3](../第四部分-训练系统/第20章-稳定性与容错.md#2043-故障检测三类问题难度递增)),目标是把 hang 的平均发现时长压到分钟级。
- **自动化栈采集**:心跳告警触发时自动对全 rank 抓栈,把"止损与采证的冲突"消掉。
- **dataloader 读超时与坏文件跳过策略**进入训练模板,消灭分支 B 中最高频的数据饿死。
- **通信调用序一致性检查**进入代码评审清单(分支 C 的预防)。
- **故障演练**:每季度注入一次人为 hang(如暂停单 rank 进程),验证检测延迟与自动处置链路(演练框架见 [§20.4.8](../第四部分-训练系统/第20章-稳定性与容错.md#2048-故障演练与-slo))。

# Runbook 03:GPU XID/ECC 硬件错误

## 现象

- 节点侧错误码告警:NVIDIA XID 事件(内核日志/DCGM 采集)或昇腾 health 状态异常(npu-smi / 健康接口),对应 [§20.4.3](../第四部分-训练系统/第20章-稳定性与容错.md#2043-故障检测三类问题难度递增) 的第一类故障——它会自己报告自己。
- 伴随形态按严重度不同:任务进程崩溃退出、CUDA/ACL 运行时报不可恢复错误、单卡从设备列表消失("掉卡")、或任务照常运行但 ECC 可纠正错误计数持续上涨。
- ECC 分两类表现:**可纠正(corrected)**——硬件已修正,任务无感,仅计数上涨;**不可纠正(uncorrected)**——数据已损坏,通常伴随进程被杀或框架报错。

## 影响范围

- **单卡 → 单节点**:一张卡的硬件错误,在全局同步训练里等于整个任务中断(所有 rank 陪停),但资源面影响通常限于该节点。
- **升级判定**:同一节点多卡同时报错 → 怀疑节点级公共件(供电、PCIe/主板、散热);同一批次/同一机柜多节点集中报错 → 怀疑批次性硬件缺陷或机房环境(温度、供电质量),升级为集群级事件并通知硬件与机房侧。
- 超节点形态下一张卡的故障域可能是整个互联域,影响面按 [§20.4.5](../第四部分-训练系统/第20章-稳定性与容错.md#2045-故障域的放大超节点改写全部容错算术重点) 的域级口径重算。

## 立即止损

1. **给节点打隔离标记(cordon)**,阻止新任务调度上来。副作用:资源池容量临时减少;此动作不影响在跑任务,先做无害。
2. **判断在跑任务是否必须立刻迁走**:出现不可纠正 ECC、掉卡、或导致进程崩溃的 XID → 任务已中断或数据不可信,立即从最近 checkpoint 在健康节点上重启,损坏窗口内的产出不可信时回滚到错误首次出现之前的 checkpoint。副作用:回滚损失训练进度(可能多回滚一个间隔以避开污染窗口);热备不足时任务需要排队。
3. **仅可纠正 ECC 计数上涨、任务未受影响**:不立刻杀任务,允许跑到下一个 checkpoint 边界再有计划地迁移。副作用:带病运行窗口内存在错误升级为不可纠正的风险,窗口越长风险越大——超过一个 checkpoint 间隔仍未迁移视为违规。
4. **驱逐(drain)节点上的其余工作负载**,节点转入检修池。副作用:同节点其他任务被迫迁移/重启,需按优先级安排顺序。

## 证据采集

- **错误码全文**:内核日志中的 XID 记录(编号、时间戳、涉及的卡)/昇腾健康接口的错误码与事件日志——错误码编号是分诊的第一依据,采集时保留上下文而不只是编号。
- **ECC 计数快照**:每张卡的可纠正/不可纠正计数、易失(本次上电)与聚合(生命周期)两套计数、退役页/行修复状态。
- **设备状态**:温度、功耗、时钟频率历史曲线(热相关故障的旁证)、PCIe/互联链路状态与降速记录。
- **任务侧对照**:错误首次出现的时间戳 vs 任务日志中 loss 异常/报错的时间戳——用于判定污染窗口,决定回滚到哪个 checkpoint。
- **节点履历**:该节点/该卡的历史报错记录与维修记录(判断"惯犯")。
- 指标采集口径见 [§29.2.4](../第七部分-工程化与治理/第29章-可观测性与评测流水线.md#2924-训练侧可观测性与告警设计);节点健康检查机制见 [§8.4.6](../第二部分-算力底座/第08章-K8s上的加速卡.md#846-节点生命周期驱动健康检查与自动隔离)。

## 诊断决策树

核心分叉:**可恢复(软件/瞬态)vs 需隔离(硬件损伤)**。

- **分支 A:应用/驱动层软件错误**(XID 语义指向用户程序非法访存、驱动状态异常等)
  - 判定依据:错误码语义为软件类;同一错误只随特定任务/特定代码出现,换任务不复现;硬件计数(ECC、退役页)无变化。
  - 结论:**可恢复,不隔离硬件**。下一步:归还节点前跑一轮压力自检确认干净;问题移交任务方修代码;若由驱动状态异常引起,重置设备或重启节点后自检。
- **分支 B:可纠正 ECC 上涨,未越阈值**
  - 判定依据:corrected 计数上涨但增速平缓,无不可纠正错误,无退役页新增或新增后已完成修复。
  - 结论:**观察名单,不立即隔离**。下一步:进入重点巡检名单,设增速告警;连续再犯(如 7 天内再次触发)升级为分支 C。
- **分支 C:可纠正 ECC 高频/加速上涨,或出现退役页持续新增**
  - 判定依据:计数增速陡增、同一存储区域反复报错、退役资源接近上限。
  - 结论:**需隔离**——这是不可纠正错误的前兆。下一步:按计划下线,走行/页修复或返修流程,修复后压测达标才可归还。
- **分支 D:不可纠正 ECC / 导致崩溃的硬件类 XID / 掉卡**
  - 判定依据:uncorrected 计数非零、错误码语义为硬件不可恢复、设备从总线消失。
  - 结论:**立即隔离**。下一步:节点保持 cordon + drain,进检修池;能通过页退役/重启自愈的,自愈后仍须通过完整压力自检;复现或无法自愈的走返修/换卡。
- **分支 E:多卡/多节点集中报错**
  - 判定依据:错误在空间(同节点多卡、同机柜多节点)或时间(同批次同时)上聚集。
  - 结论:**升级为公共件/批次事件**。下一步:排查供电、散热、机房环境与批次固件;在根因确认前,同特征节点全部列入嫌疑名单加密巡检。
- **静默数据错误提示**:若任务出现 loss 异常但无任何错误码,不属于本 Runbook——那是 SDC,按 [§20.4.3](../第四部分-训练系统/第20章-稳定性与容错.md#2043-故障检测三类问题难度递增) 第三类故障处置(回滚 + 巡检定位"会算错的卡")。

## 修复

- **节点隔离流程(分支 C/D/E 统一)**:cordon → drain → 打检修标签并记录错误证据 → 检修池内离线诊断(厂商诊断工具 + 压力测试)→ 修复动作(页/行退役、重置、换卡、返修)→ **入池门禁**:满负载压力自检 + 通信基准达标 → uncordon 归还资源池。全程状态机与自动化要求见 [§8.4.6](../第二部分-算力底座/第08章-K8s上的加速卡.md#846-节点生命周期驱动健康检查与自动隔离)。
- **任务侧**:从污染窗口之前的 checkpoint 恢复;若错误与任务代码相关(分支 A),推动任务方修复后再上大规模。
- **容量侧**:热备池补位;热备耗尽时按优先级抢占或缩容低优任务,维持高优训练的资源规格。

## 恢复验证

- **节点侧**:压力自检(满负载计算 + 显存全量读写 + 通信基准)通过;自检期间及其后 24 小时 ECC 计数零新增、无新 XID;温度/功耗曲线正常。
- **任务侧**:从 checkpoint 恢复后 loss 曲线与历史吻合;连续一个 checkpoint 间隔无错误码告警;单步时长回到基线 ±5%。
- **归还验证**:被隔离节点归还后,首个调度上去的任务跑满 24 小时无同类告警,方可移出观察名单。

## 复盘数据

- **检测延迟**:错误码首次出现 → 告警触发(第一类故障应为秒级到分钟级,超过 5 分钟说明采集链路有洞)。
- **隔离时长**:告警 → 节点完成 cordon;**处置时长**:cordon → 任务在健康资源上恢复训练。
- **中断时长与损失卡时** = 任务停止推进时长 × 卡数 + 回滚步数 × 单步时长 × 卡数(污染窗口导致的多回滚单列)。
- **节点在检修池的停留时长**与修复动作记录(用于核算备机率与 MTTR)。
- 错误码类型、分支(A–E)、卡/节点序列号、是否惯犯(同一硬件 90 天内重复故障)。
- 汇入集群失败率模型与 [§20.4.2 有效训练时间占比](../第四部分-训练系统/第20章-稳定性与容错.md#2042-有效训练时间占比稳定性的唯一北极星指标) 月度核算。

## 长期防复发

- **错误码采集与自动隔离链路**:错误码 → 告警 → 自动 cordon 的处置延迟目标定为分钟级,人工只做复核([§8.4.6](../第二部分-算力底座/第08章-K8s上的加速卡.md#846-节点生命周期驱动健康检查与自动隔离))。
- **ECC 趋势监控**:对可纠正计数设增速告警而非绝对值告警,把分支 C 提前到分支 D 发生之前。
- **周期性巡检**:空闲时段跑已知答案校验,兼顾 SDC 与"亚健康卡"的提前发现([§20.4.3](../第四部分-训练系统/第20章-稳定性与容错.md#2043-故障检测三类问题难度递增))。
- **入池门禁制度化**:任何节点(新装、返修、长期闲置)入池前必须通过统一自检基准。
- **备机率核算**:按集群失败率模型([§20.4.1](../第四部分-训练系统/第20章-稳定性与容错.md#2041-失败率模型故障为什么是常态))与实际 MTTR 定期校准热备池规模;超节点集群按域级故障口径加算([§20.4.5](../第四部分-训练系统/第20章-稳定性与容错.md#2045-故障域的放大超节点改写全部容错算术重点))。

# Lab 08:InferencePool 与 EPP——模型感知的实例选择层

| 项 | 值 |
|---|---|

## 目标

做完本 Lab 你能回答:第 27 章说的"四层决策"里,第三层——同一模型的众多实例里选哪一个——做成标准 API 之后长什么样。具体做法是在 K8s 集群安装 Gateway API Inference Extension,建一个 InferencePool 圈住同一模型的多个副本,配上参考实现的 Endpoint Picker(EPP),然后从两个方向观察它的行为:请求级(同前缀请求是否稳定落到同一实例,即缓存/负载信号驱动的实例选择)与发布级(HTTPRoute 按权重挂两个池,灰度分流是否生效)——亲眼看到"哪个模型/版本由 HTTPRoute 回答、哪个实例由池内 EPP 回答"这条分层边界。

## 步骤

1. **准备集群与网关。** 一个可用的 K8s 集群,安装 Gateway API 标准 CRD 与一个支持推理扩展的网关实现(以推理扩展官方文档当期列出的兼容实现为准,如 Envoy 系网关);再安装 Gateway API Inference Extension 的 CRD(InferencePool 及配套资源)。
2. **部署模型实例组。** 用同一个小模型部署一个多副本(≥2)的 vLLM 类推理 Deployment,开启前缀缓存,每副本一卡;给 Pod 打上统一 label 作为池的 selector。
3. **建 InferencePool 与 EPP。** 创建 InferencePool 资源,以上述 label 圈定副本;按扩展的参考部署方式起 EPP(Endpoint Picker),让网关把到达该池的请求交 EPP 打分选实例。确认 EPP 日志或 metrics 能看到它拿到的路由信号(队列深度、前缀缓存等信号,具体取决于所装版本启用的 scorer/插件)。
4. **接通请求路径。** 建 HTTPRoute,把某个路径/主机名的流量指向该 InferencePool(而非普通 Service);端口转发网关后发一条推理请求验证链路通。
5. **观察实例级选择(缓存/负载信号)。** 复用 Lab 07 的负载生成思路:多个会话、每会话多轮、共享长系统提示词。发压后从三处取证:(a) 网关/EPP 日志中每请求被选中的目标 Pod;(b) 各实例 metrics 的前缀缓存命中计数;(c) 各实例的排队/负载指标。预期方向:同前缀(同会话)的后续请求稳定落到同一实例,整体命中率显著高于把同批负载打向绕过 EPP 的普通 Service(可以另建一条指向普通 Service 的 HTTPRoute 作对照组,复现 Lab 07 的随机基线)。
6. **观察发布级分流(灰度分池)。** 再部署第二个实例组模拟"新版本"(同一模型也可,label 区分),建第二个 InferencePool 与其专属 EPP;把 HTTPRoute 改为两池按权重分流(如 90/10)。发一批带新会话的请求,统计两池实际接到的请求比例是否与权重一致;同时观察切到新池的会话经历命中率从零重建——这就是第 27 章冲突矩阵第一行"灰度切流 vs 前缀亲和"的现场版。
7. **(可选)验证信号隔离。** 确认 EPP 的信号视野限于自己的池:新池 EPP 的日志里看不到旧池实例的负载与缓存状态——对应冲突矩阵第三行"多池灰度 vs 信号隔离"。

## 成功判据

- 经 InferencePool + EPP 的路径上,同前缀请求稳定落到同一实例(EPP 选择日志与实例命中计数两处证据一致),整体前缀缓存命中率明显高于普通 Service 对照组,方向与 §24.4.5"缓存感知调度"档的预期一致;
- 两池按 HTTPRoute 权重分流,实测请求比例与配置权重吻合(样本量足够时偏差收敛);
- 能指出分层边界的证据:改 HTTPRoute 权重只影响池间流量分配、不改变池内实例选择;改 EPP/池内副本只影响池内选择、不影响池间比例;
- 切流瞬间新池命中率从零爬升的过程在监控上可见(冲突矩阵第一行的复现)。

## 清理步骤

集群级 Lab,必须清理:

- 删除 HTTPRoute、两个 InferencePool 及 EPP 部署;
- 删除两个模型实例组的 Deployment/Service,确认 GPU 节点显存释放;
- 卸载实验安装的 Inference Extension CRD 与网关实现(若集群为共享环境,先确认无他人使用);
- 按量计费集群:确认节点缩容或集群销毁。

## 常见失败与排查

- **请求 404/503,链路不通**:先分段验证——直接端口转发单个模型 Pod 能推理吗?网关到普通 Service 通吗?最后才查 InferencePool/EPP;多数问题出在网关实现与推理扩展的版本兼容矩阵,以扩展官方文档当期的兼容列表为准。
- **EPP 在选实例但看不出亲和**:检查所装版本默认启用了哪些打分插件——若只启用了负载/队列 scorer 而未启用前缀缓存 scorer,行为退化为负载均衡;确认前缀相关 scorer 已启用后重测。
- **权重分流比例不准**:小样本下偏差正常;另查是否有客户端/网关层连接复用把同连接请求粘到同一后端,换用每请求新建连接或提高样本量。
- **切流后 TTFT 尖峰误判为故障**:先想冲突矩阵第一行——这是命中率重建期的预期表现,用第 24 章三因子公式估算损失量级,再决定是否放粗切流粒度,而不是回滚。

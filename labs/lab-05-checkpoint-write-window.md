# Lab 05:Checkpoint 写入窗口基准

| 项 | 值 |

## 目标

做完本 Lab,你能回答:

1. 你的目标存储(本地 NVMe / 并行文件系统 / 对象存储挂载)单客户端持续写带宽实际是多少——不是标称,是从你这个节点、以 checkpoint 的写模式(大块顺序写)测出来的数;
2. 给定一个目标模型,checkpoint 大小、写入窗口 T_write、建议保存间隔三个数怎么在任务提交前算出来([§14.4.3](../第三部分-数据底座/第14章-存储与Checkpoint-IO.md#1443-checkpoint-的突发写模式本章核心) 的五步估算清单);
3. "把 T_write 压短"为什么同时买到了"敢于更频繁保存"的权利(Young 近似的杠杆方向)。

## 步骤

**第一步:选定目标与模型规格。** 确定要评估的存储路径(如 `/mnt/pfs/ckpt-lab/`)与目标模型参数量 N。先手算 checkpoint 大小:

> S_ckpt ≈ N × 16 字节(BF16 混合精度 + Adam 完整训练态,[§14.4.3](../第三部分-数据底座/第14章-存储与Checkpoint-IO.md#1443-checkpoint-的突发写模式本章核心))

例如 7B 模型约 112 GB、70B 约 1.1 TB。本 Lab 的写测试量取 S_ckpt 的缩小版即可(几十 GB 足以摸到持续带宽),不必真写 1.1 TB。

**第二步:测持续写带宽。** 用 fio 模拟 checkpoint 的写模式——大块、顺序、单进程与多进程各测一轮:

```bash
# 单写者:模拟一个 rank 写一个大分片
fio --name=ckpt-1w --directory=/mnt/pfs/ckpt-lab --rw=write --bs=16m \
    --size=32g --ioengine=libaio --iodepth=8 --direct=1 --numjobs=1 --group_reporting

# 多写者:模拟一个节点上多个 rank 并发写(numjobs 取每节点保存进程数)
fio --name=ckpt-8w --directory=/mnt/pfs/ckpt-lab --rw=write --bs=16m \
    --size=8g --numjobs=8 --ioengine=libaio --iodepth=8 --direct=1 --group_reporting
```

没有 fio 时的最简替代:`dd if=/dev/zero of=/mnt/pfs/ckpt-lab/test bs=16M count=2000 oflag=direct conv=fsync`(注意 `oflag=direct` 与结尾 fsync,否则测的是页缓存)。记录两轮的聚合带宽 B_client(GB/s),以及多写者相对单写者是否线性——不线性说明单客户端(网卡或挂载协议)已是短板。

**第三步:手算写入窗口。** 按 [§14.4.3](../第三部分-数据底座/第14章-存储与Checkpoint-IO.md#1443-checkpoint-的突发写模式本章核心) 的清单走:

1. S_ckpt = 16N;
2. 数参与写的**节点数** M(分片保存 = 全体节点;聚合到单点 = 1);
3. 聚合客户端带宽 = M × 本节点实测 B_client;存储侧聚合写带宽 B_storage 从存储规格取并按 60% 打折(读写混合折扣)——单机自测时无法实测 B_storage,注明这是规格代入值;
4. T_write = S_ckpt ÷ min(聚合客户端带宽, 打折后 B_storage);数千 rank 各写一文件时给 T_write 加 30 秒~2 分钟的元数据固定开销;
5. 检查 T_write / 计划间隔 是否 ≤ 1%。

**第四步:用估算器复算并求建议间隔。** 把实测带宽代入本书 calculators 的 checkpoint 估算器(MTBF 按你集群的实际估计,没有数据时用 [§20.4.1](../第四部分-训练系统/第20章-稳定性与容错.md#2041-失败率模型故障为什么是常态) 的规模换算做量级假设并写明):

```bash
PYTHONPATH=calculators/src python3 -m ai_infra_calc checkpoint \
  --n-params-b 70 --client-bw-gbps <M×实测B_client> \
  --storage-bw-gbps <打折后B_storage> --mtbf-hours <你的估计>
```

对账三处:估算器的"单次快照大小"应等于你手算的 16N;"全量写入时长"应等于你第三步的 T_write(同为 min 短板除法);"建议保存间隔"应与 Young 近似 √(2 × 停顿时长 × MTBF) 的手算一致。三处任何一处对不上,先怀疑单位换算(GB/GiB、bit/Byte)。

**第五步:做一次杠杆实验(纸面)。** 保持其他输入不变,把带宽调大 10 倍(模拟改用本地 NVMe 两级方案)重跑估算器:观察 T_write 与建议间隔如何同时缩短、单次故障平均回滚损失(≈ 间隔一半)如何下降——这就是 [§14.4.3](../第三部分-数据底座/第14章-存储与Checkpoint-IO.md#1443-checkpoint-的突发写模式本章核心) 结尾"优化写入窗口是买到敢于频繁保存的权利"的数字化验证。

## 成功判据

- 得到目标存储的单节点持续写带宽实测值(单写者与多写者两组),并能说明哪一层是短板;
- 手算的 S_ckpt、T_write、建议间隔与估算器输出**逐项自洽**(同一输入下数值一致,而非"差不多");
- T_write 的量级与 [§14.4.3](../第三部分-数据底座/第14章-存储与Checkpoint-IO.md#1443-checkpoint-的突发写模式本章核心) 按规模分档表中你所处档位的量级相符(用你的实测带宽代入,不套用表中数字);
- 能向任务负责人交付一句完整结论:"该模型 checkpoint X GB,当前存储写完约 Y 秒,建议间隔 Z 分钟,开销占比 W%"。

## 清理步骤

- 删除全部测试文件:`rm -rf /mnt/pfs/ckpt-lab/`(fio 与 dd 的产物都在此目录);
- 共享存储上通知管理员测试结束;
- 若为测试临时放宽了配额或 QoS 限速,恢复原设置。

## 常见失败与排查

1. **测出的带宽好得不像话(远超网卡线速)**:写进了页缓存。确认 `--direct=1` / `oflag=direct` 生效,且测试量显著大于内存;对象存储挂载(FUSE 类)可能不支持 direct IO,此时加大测试量并以 fsync 完成时间计带宽。
2. **多写者带宽不升反降**:单客户端网卡或挂载协议已饱和,或存储侧对单客户端限流——这正是 B_client 的真实上限,按实测值用,不要取单写者×进程数。
3. **实测带宽远低于存储标称聚合带宽**:标称是全集群聚合值,单节点摸不到;聚合口径要靠多节点同测(L3),单机版按"M × 单节点实测"外推并注明假设。
4. **建议间隔算出来短于 T_write**:说明该存储根本撑不住这个模型的同步保存——结论不是调参数,而是上两级方案(先写本地 NVMe 异步上传)或分片保存,见 [§14.5.1](../第三部分-数据底座/第14章-存储与Checkpoint-IO.md#1451-三种-checkpoint-优化)。

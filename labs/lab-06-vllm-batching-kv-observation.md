## 目标

做完本 Lab,你能回答:

1. 推理引擎的三个内部状态——running 批、waiting 队列、KV 池水位——在阶梯加压下如何联动,为什么它们(而不是 GPU 利用率)才是容量指标;
2. 你这套"模型 + 卡 + 上下文分布"的并发拐点在哪里:吞吐随并发爬升到何处开始平台化、TPOT 从何处开始恶化、waiting 从何处开始堆积;
3. 这个拐点能否被 F8/F9 提前算出来——用纸面算的并发上限对照实测拐点,完成 [§22.1](../第五部分-推理系统/第22章-推理引擎原理.md#221-kv-cache-与显存) "推理并发上限是显存账决定的"这一论断的闭环。

## 步骤

**第一步:起服务并抄下形状参数。** 选一个单卡装得下的开源模型(数 B 参数量级),启动 vLLM 的 OpenAI 兼容服务(命令形态,不锁版本):

```bash
vllm serve <模型名或本地路径> --port 8000
```

从模型的 config(或启动日志)抄下 F8 需要的参数:层数 L、KV 头数 a_kv、头维度 d_head、KV 精度 p;从启动日志抄下引擎实际预留的 **KV 池大小**(vLLM 会打印可用 KV cache 的 GiB 数或块数×块大小)。

**第二步:纸面预测拐点。** 设定一个固定的请求形状(如输入 1024 token、输出 256 token,后续加压全用它),按 [§22.2.4 算账小节](../第五部分-推理系统/第22章-推理引擎原理.md#2224-把本章的账合起来算一次) 的口径:稳态人均驻留 ≈ 输入 + 输出/2 ≈ 1152 token。用本书 calculators 复算:

```bash
PYTHONPATH=calculators/src python3 -m ai_infra_calc kv \
  --layers <L> --kv-heads <a_kv> --head-dim <d_head> --kv-precision <p> \
  --kv-pool-gib <日志里的KV池> --avg-context-tokens 1152
```

记下两个预测数:每 token KV 字节数(F8)与并发上限(F9)。这是你的**预注册预测**,写下来再开始实测——先测后算容易骗自己。

**第三步:接好观测。** vLLM 暴露 Prometheus 指标端点:

```bash
watch -n 2 'curl -s localhost:8000/metrics | grep -E \
  "num_requests_running|num_requests_waiting|gpu_cache_usage_perc" | grep -v "^#"'
```

有 Prometheus/Grafana 更好;没有就用上面的 watch 循环,每档负载抄一次三个数。TPOT 与吞吐从压测端取。

**第四步:阶梯加压。** 用 vLLM 自带的基准客户端(`vllm bench serve`,旧版本为 benchmark_serving 脚本)或任何能控制并发数的压测工具,固定请求形状,并发按阶梯上升——例如从预测上限的 1/8 开始,按 ×2 逐档,直到预测上限的 2 倍。每档持续到指标稳定(至少几十秒),记录五元组:

> 并发档位 → running、waiting、gpu_cache_usage_perc、总吞吐(token/s)、TPOT(均值与 P99)

**第五步:找三个特征点并画图。** 以并发为横轴画四条曲线(吞吐、TPOT、KV 水位、waiting),标出:

1. **吞吐平台点**:吞吐不再随并发线性上升的位置——对应 decode 批攒够、单步访存被摊满([§22.2.1 Continuous Batching](../第五部分-推理系统/第22章-推理引擎原理.md#2221-continuous-batching));
2. **KV 触顶点**:gpu_cache_usage_perc 逼近高位、running 不再增长、waiting 开始堆积的位置——这就是 F9 拐点的实测形态;此后加压只加深队列,不加吞吐;
3. **TPOT 恶化点**:P99 TPOT 显著抬升的位置,注意它与前两点的先后关系;若观察到抢占(vLLM 有抢占计数指标),对照 [§22.2.3 抢占小节](../第五部分-推理系统/第22章-推理引擎原理.md#2223-优先级抢占与请求驱逐) "抢占率持续偏高 = 容量规划错了"。

**第六步:与预测对账。** 实测的 running 饱和值对照第二步 F9 预测的并发上限:两者应同量级(引擎按水位留余量、块粒度取整、实际输出长度分布都会造成系数级偏差,能解释即可)。再反向验算 F8:KV 池大小 × 实测水位 ÷ (running × 人均驻留 token) 应落在每 token KV 字节数附近。最后改一个变量重跑一遍缩短版(例如输入长度翻倍),验证并发上限近似减半——F9 的线性规律。

## 成功判据

- 观测到明确的 KV 触顶拐点:running 封顶、waiting 转为堆积、吞吐平台化三者在相近并发档位发生——即"并发受 KV 池上限约束"被直接看见,而非推断;
- 实测 running 饱和值与 F9 纸面预测同量级,偏差方向可解释(水位余量、长度方差、块内碎片);
- F8 反算的每 token KV 字节数与模型形状代入值同量级;
- 能画出并讲解"并发-吞吐-TPOT-KV 水位"四线图,指出这套部署应把限流阈值设在哪一档、为什么(对照 [§22.2](../第五部分-推理系统/第22章-推理引擎原理.md#222-批处理与调度) 的准入控制视角)。

## 清理步骤

- 停止 vLLM 服务与压测进程,`nvidia-smi` 确认显存已释放;
- 删除压测输出与临时下载的数据集文件;共享机器上删除下载的模型权重或移入团队共享缓存目录,避免每人一份。

## 常见失败与排查

1. **加大并发吞吐一直线性涨、看不到拐点**:模型太小或 KV 池太大,拐点在你的压测上限之外——用 `--max-model-len` 收紧或换更长的请求形状,把 F9 上限压进可测范围;这本身就是一次"用公式设计实验"的练习。
2. **还没触到 KV 上限 TPOT 就先恶化**:检查是否有长 prompt 混入触发 Prefill 阻塞([§22.2.2 Chunked Prefill](../第五部分-推理系统/第22章-推理引擎原理.md#2222-chunked-prefill长-prompt-饿死-decode)),或并发档切换太快、未等稳态;固定请求形状与预热时间后重测。
3. **metrics 端点抓不到上述指标**:指标名随版本有前缀/命名差异,先 `curl localhost:8000/metrics | grep -i cache` 摸清本版本命名再改抓取式。
4. **容量与容器层显存监控对不上**:KV 池是启动时一次性预分配的,容器层显存占用恒接近满、与负载无关——必须用引擎侧指标,原因见 [§22.1](../第五部分-推理系统/第22章-推理引擎原理.md#221-kv-cache-与显存) 与第 25 章弹性指标的讨论。

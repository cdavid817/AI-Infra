# Lab 07:Prefix Cache 与请求亲和性——复现 P_路由 因子

| 项 | 值 |
|---|---|
| 等级 | L1 单 GPU(单卡跑两实例的缩小版)/ L2 单机多 GPU(每实例独占一卡,推荐) |
| 预计资源与成本 | 1–2 张卡 × 1–2 小时;用 7B 级或更小的模型即可,无需大模型 |
| 安全风险 | 无(全部流量在本机回环地址,不出网) |
| 关联章节 | [§24.4.3 Prefix Cache:命中率模型与三级缓存](../第五部分-推理系统/第24章-服务化架构与显存类加速.md#2443-prefix-cache命中率模型与三级缓存) 的三因子公式 $h = h_{\max} \times P_{\text{路由}} \times P_{\text{驻留}}$;[§24.4.5 前缀感知路由](../第五部分-推理系统/第24章-服务化架构与显存类加速.md#2445-前缀感知路由路由策略与命中率的耦合讲透) 的 $P_{\text{路由}} \approx 1/N$ 结论 |

## 目标

做完本 Lab 你能回答:为什么"引擎开着 Prefix Cache、单实例压测命中率很高,上了多实例命中率却崩了"。具体做法是亲手搭一个 N=2 的最小复现场景:同一批多轮对话请求,分别经过**随机路由**与**前缀亲和路由**打到两个引擎实例上,对比两种路由下的缓存命中率与 TTFT,验证第 24 章的结论——随机路由把 $P_{\text{路由}}$ 打到约 $1/N$,而这不是引擎问题,是路由问题。

## 步骤

1. **起两个引擎实例。** 用 vLLM 或 SGLang 在本机起两个实例,监听不同端口(如 8001、8002),加载同一个小模型,并打开前缀缓存(vLLM 为 `--enable-prefix-caching`,SGLang 默认开启 RadixAttention)。L1 缩小版:单卡上用显存比例参数(如 vLLM 的 `--gpu-memory-utilization`)各分一半显存跑两个实例;L2 版:各实例独占一卡。确认两实例的 metrics 端点(`/metrics`)都能抓到前缀缓存的查询数与命中数(vLLM 有 prefix cache queries/hits 计量;SGLang 在日志与 metrics 中报 cache hit rate)。
2. **构造有前缀重复的负载。** 写一个生成脚本:固定一段较长的系统提示词(千 token 量级),模拟 M 个会话、每会话多轮,第 k+1 轮的 prompt = 系统提示词 + 前 k 轮拼接历史 + 少量新输入。这个负载的 $h_{\max}$ 很高且可以从构造方式直接算出来(每轮新增 token / 累计 prompt token,参照 §24.4.3 对多轮对话负载的刻画)。
3. **写一个几十行的路由脚本。** 一个最简 HTTP 代理,收到请求后按两种策略之一选后端:
   - `random`:均匀随机选 8001 或 8002;
   - `affinity`:按会话 ID(或 prompt 前 k 个字符的哈希)一致性哈希,同会话永远落同一实例——即 §24.4.5 三档策略里的第一档"会话粘性"。
4. **跑随机路由组。** 清空/重启两实例(保证缓存从零开始),以 `random` 策略回放整批负载,记录:每请求 TTFT(客户端测首 token 时间),以及两实例 metrics 中的前缀缓存命中 token 数与查询 token 数,算出全局命中率 $h_{\text{random}}$ 。
5. **跑亲和路由组。** 再次重启两实例清空缓存,以 `affinity` 策略回放同一批负载,同样记录 TTFT 与全局命中率 $h_{\text{affinity}}$ 。
6. **对账。** 用三因子公式对两组数据做归因:两组的 $h_{\max}$ 相同(同一批负载)、 $P_{\text{驻留}}$ 近似相同(缓存容量远大于工作集时接近 1),差异应几乎全部由 $P_{\text{路由}}$ 解释——随机组约 $1/N = 1/2$,亲和组接近 1。同时对比两组 TTFT 分布(命中的前缀免 prefill,亲和组多轮请求的 TTFT 应系统性更低,幅度与命中省掉的 prefill token 量同向)。
7. **(可选)扩展 N。** 若卡够多,把实例数加到 3–4 个重跑随机组,观察命中率随 N 继续下滑——复现"横向扩容反而降低命中率"这一反直觉规模效应。

## 成功判据

- 随机路由组的全局命中率趋近 $h_{\max} \times 1/N$(N=2 时约为亲和组的一半),与 §24.4.5 的 $P_{\text{路由}} \approx 1/N$ 模型方向一致、量级吻合;
- 亲和路由组命中率趋近 $h_{\max}$(会话内前缀几乎全命中);
- 亲和组中多轮会话第 2 轮及以后请求的 TTFT 明显低于随机组同位置请求,且差距随会话轮数(即可复用前缀长度)增长——与"命中一段前缀就免去这段 prefill"的机制一致;
- 你能用测得的三因子把两组命中率差异完整归因,不需要引入引擎差异或模型差异作解释。

## 清理步骤

- 终止两个引擎实例进程与路由脚本,确认 GPU 显存释放(`nvidia-smi` 无残留进程);
- 删除负载生成脚本产出的请求数据与结果 CSV(或归档到实验目录);
- 若修改过引擎的缓存相关配置,恢复默认。

## 常见失败与排查

- **两组命中率几乎一样高**:多半是负载回放时并发太低、请求按会话顺序串行发出,随机路由下相邻请求恰好被"轮空"到同一实例;提高并发、打乱会话间的发送顺序,让路由的随机性真正生效。
- **亲和组命中率也上不去**:检查系统提示词是否逐字节稳定——时间戳、随机 request ID 拼进了 prompt 开头会打断哈希链,参见 §24.4.3 对"时间戳打零 $h_{\max}$"的机械解释。
- **命中率读数对不上**:vLLM/SGLang 的命中率口径是 token 级还是块级、是累计值还是区间值,不同版本有差异;以 metrics 的原始计数器(查询 token 数、命中 token 数)自行做差计算区间命中率,不直接读比率型指标。
- **单卡双实例 OOM 或互相挤占**:两实例显存比例之和留出余量(激活与碎片),或换更小的模型;这是 L1 缩小版的固有约束,结论不受影响,受影响的只是可承载的并发。

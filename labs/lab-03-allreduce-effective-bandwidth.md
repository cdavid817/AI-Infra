## 目标

做完本 Lab,你能回答:

1. Ring AllReduce 每卡通信量 $\approx 2S(n-1)/n$ 这个系数,在真实基准的 busbw(总线带宽)定义里如何体现;
2. 你的机器(和集群)在什么消息大小之后进入带宽平台区、平台区的 $B_{eff}$ 是标称带宽的几成——从此你的 F20 估算就有了自己实测的 $B_{eff}$,不再抄书;
3. 同一 AllReduce,域内与跨机的 $B_{eff}$ 差多少倍——亲手量出 [§7.4.4](../第一部分-基础与心智模型/第07章-互联与集合通信.md#744-互联域与三级拓扑本章核心) 那道"断崖"。

## 步骤

**第一步:准备基准工具。** NVIDIA 路径用 nccl-tests(随 NGC 容器附带,或从源码 `make` 构建,不锁版本);昇腾路径用 HCCL 的对应基准与 `ranktable` 组网,工具对照见 [§5.3](../第一部分-基础与心智模型/第05章-CUDA、CANN与加速器软件栈.md#53-cann-与昇腾软件栈两套完整并行的世界) 与 [§7.4.5](../第一部分-基础与心智模型/第07章-互联与集合通信.md#745-hccl-与昇腾互联),测量与对账方法完全相同。

**第二步:消息大小扫描(单机)。**

```bash
# n 取本机卡数;-b/-e 为起止消息大小,-f 2 表示每次翻倍
./build/all_reduce_perf -b 1K -e 4G -f 2 -g <n>
```

记录每个消息大小的 algbw 与 busbw 两列。先做一次定义对账:nccl-tests 的 busbw = algbw × $2(n-1)/n$——正是 [§7.4.2](../第一部分-基础与心智模型/第07章-互联与集合通信.md#742-集合通信原语四个动词与它们的通信量) Ring AllReduce 每卡线上量系数。用任意一行数据手工验算这个换算,确认自己读懂了两列的含义(algbw 面向"任务视角"的数据量 ÷ 时间,busbw 面向"链路视角"的实际线上流量,后者才能与硬件标称对比)。

**第三步:画曲线,找两个特征量。** 以消息大小为横轴(对数)、busbw 为纵轴作图:

- **平台区带宽 $B_{eff}$**:大消息端的渐近值。与你这台机器卡间互联的标称带宽(见 [附录 A.1](../附录/附录A-加速卡与集群形态速查表.md#a1-主流加速卡参数对照) 或厂商 spec)对比,算出折扣系数——应落入 [§7.4.6](../第一部分-基础与心智模型/第07章-互联与集合通信.md#746-通信量估算每步多少字节走哪条线) "有效带宽按标称 60~80%"的区间附近;明显更低则说明有问题(见排查);
- **拐点消息大小**:busbw 达到平台一半的位置。小消息端由启动延迟项主导(F20 的第二项),这就是"小消息测不出带宽、大消息才摸到墙"的直观呈现。

**第四步:rank 数扫描。** 固定一个平台区消息大小(如 1G),把 `-g` 从 2 扫到本机卡数,观察 busbw 随 rank 数的变化。理论上 Ring 的 busbw 上限不随 n 变化(系数 $2(n-1)/n$ 已归一进定义),实测常见轻微下降(环更长、慢链路概率更大)——若某个 n 骤降,对照 [Lab 02](lab-02-gpu-topology-discovery.md) 的拓扑图检查是不是环跨过了一条低速链路(短板效应)。

**第五步(L3,可选):跨机对比。** 两台机器各出等量卡,重复第二、三步:

```bash
mpirun -np <总卡数> -H host1:<n>,host2:<n> ./build/all_reduce_perf -b 1K -e 4G -f 2 -g 1
```

对比域内与跨机的平台区 busbw,并与集群网络的标称(每卡 RDMA 带宽)对账。**缩小替代**:没有多机额度时,用 [§7.4.4](../第一部分-基础与心智模型/第07章-互联与集合通信.md#744-互联域与三级拓扑本章核心) "跨域跌 5~10 倍"的量级加上你集群网卡标称做纸面推算,后续步骤照做。

**第六步:回填估算器,对账 F20。** 用第三步(和第五步)测出的 $B_{eff}$ 回填本书 calculators 的 comm 估算器,复算 [§7.4.6](../第一部分-基础与心智模型/第07章-互联与集合通信.md#746-通信量估算每步多少字节走哪条线) 的 70B 梯度 AllReduce 场景:

```bash
PYTHONPATH=calculators/src python3 -m ai_infra_calc comm \
  --collective allreduce --payload-gb 35 --ranks 8 --bus-bw-gbps <你的实测Beff>
```

分别代入域内与跨机的 $B_{eff}$,确认"同一公式换一个 $B_{eff}$,结论差一个量级"在你自己的数字上成立。最后写三行结论:标称带宽、实测 $B_{eff}$ 、差距的解释(协议开销、环拓扑、是否跨低速链路)。

## 成功判据

- 手工验算过 busbw = algbw × $2(n-1)/n$,能解释两列的差别;
- 得到本机的消息大小-busbw 曲线,平台区 $B_{eff}$ 与标称的折扣比在可解释范围(量级上与 §7.4.6 的 60~80% 口径一致;显著偏离时能给出拓扑或配置层面的解释,而不是接受一个解释不了的数);
- 实测 $B_{eff}$ 已回填 comm 估算器,估算器输出的耗时与"通信量 ÷ 实测 busbw"的手算结果自洽(同一量级、差异可归因于延迟项);做了跨机对比的,域内/跨机耗时比与两个 $B_{eff}$ 之比一致。

## 清理步骤

- 结束所有基准进程,确认卡上无残留进程(`nvidia-smi` 查看);
- L3 模式:释放申请的节点/队列资源,删除临时的 hostfile 与容器;
- 把测得的 $B_{eff}$ 记入你团队的集群参数档案(这是本 Lab 最有复用价值的产物)。

## 常见失败与排查

1. **平台区带宽远低于标称的一半**:先跑 [Lab 02](lab-02-gpu-topology-discovery.md) 确认环没有跨过 PCIe/跨 NUMA 链路;再用 `NCCL_DEBUG=INFO` 看 NCCL 实际选择的传输方式(P2P/SHM/NET)与算法,常见原因是 P2P 被禁用或容器缺设备挂载。
2. **跨机成绩接近甚至等于 TCP 网卡水平**:GPUDirect RDMA 未生效或流量落到了以太网口,检查网卡亲和([§8.4.4](../第二部分-算力底座/第08章-K8s上的加速卡.md#844-三种亲和及其冲突))与 NCCL 网络插件配置;网络故障形态的系统排查见 [§7.4.8](../第一部分-基础与心智模型/第07章-互联与集合通信.md#748-网络故障的表现形式与排查)。
3. **小消息波动大、结果不可复现**:小消息端由延迟主导,受 CPU 调度与邻居流量干扰大——对账只用平台区数据;共享集群上尽量申请独占节点再测。
4. **昇腾侧初始化失败**:第一嫌疑是 `ranktable` 组网文件写错([§7.4.5](../第一部分-基础与心智模型/第07章-互联与集合通信.md#745-hccl-与昇腾互联)),先核对设备 IP 与 rank 分布再排查其他。
